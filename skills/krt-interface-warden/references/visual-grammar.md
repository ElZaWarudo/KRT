# Visual Grammar

Use this reference when a frontend needs stronger identity than generic card grids, marketing heroes, soft shadows, glass panels, and decorative gradients.

## Avoid by Default

- Large-radius cards with soft shadows and generic padding.
- Bento grids without a strong functional reason.
- Centered hero sections with generic title, subtitle, and CTA.
- Decorative background gradients.
- Glassmorphism.
- Floating icons that do not operate or explain anything.
- Generic SaaS illustrations.
- Repeated "title + text + three cards" sections.
- Metrics inside identical cards.
- Personality-free pill buttons.
- Empty white space that does not create structure.
- Interfaces that could belong to any startup.

## Primary Elements

### Bands

Use horizontal or vertical bands to separate reading moments, workflow stages, system states, or persistent actions.

Examples: top context band, side navigation band, status band, bottom action band.

### Rails

Use narrow columns to guide navigation or keep metadata visible.

Examples: left section rail, right history rail, validation rail, top progress rail.

### Annotated Margins

Treat margins as active space, not decorative emptiness.

Use them for notes, dates, owners, warnings, cross-references, review marks, counts, and status indicators.

### System Marks

Do not default to generic badges. Make states look like marks produced by the system.

Examples: Validated, Pending, Blocked, In review, Archived, Requires action.

They can appear as stamps, flat labels, margin marks, status lines, typographic indicators, or table-side signals.

### Expressive Tables

Do not hide structured data inside cards. When there is tabular data, use tables with character.

A strong table may include clear typographic hierarchy, fine separators, sticky columns, margin states, row actions, groups by date/priority/owner, and adjustable density.

### Layers

Create depth through function, not soft decoration.

Examples: main panel, inspector panel, drawer, review overlay, timeline, comparison view.

### Legends

Complex interfaces should read like maps. Include legends when colors, symbols, states, priorities, flows, or special marks appear.

### Connection Lines

When entities relate to each other, show the relationship with lines, grouping, indentation, connectors, sequence, or cross-references. Avoid isolating relationships inside disconnected cards.

## Layout Guidance

Favor:

- Asymmetric but balanced compositions.
- One dominant working column.
- Secondary rails for context.
- Active margins.
- Visible separators.
- Long reading zones.
- Inspection panels.
- Persistent navigation.
- Editorial hierarchy.

Avoid layouts where every module has equal visual weight. A working surface needs priority, tension, and a clear path of attention.

## Typography

Use a sober combination:

- A clear sans serif for general reading.
- A monospaced or semi-monospaced face for metadata, IDs, codes, dates, statuses, and technical values.
- Editorial headings with presence, not necessarily huge size.
- Avoid landing-page hierarchy unless the surface is truly a landing page.

Typography should communicate precision, system, and craft.

## Color

Use color with intent, not decoration.

Recommended base:

- Warm or neutral background instead of pure white when appropriate.
- Dark ink-like primary text.
- Fine separator lines.
- One accent for actions.
- A second accent only for state or alert semantics.

Color should signal action, state, risk, grouping, navigation, or priority.

Do not use decorative gradients unless they represent real information.

## Containers

Replace floating boxes with:

- Dividing lines.
- Partial frames.
- Marked corners.
- Proximity grouping.
- Flat backgrounds.
- Density shifts.
- Section headers.
- Editorial separators.
- Docked panels.
- Work zones.

Containers should feel like parts of a system, not isolated little boxes.

## Interaction Language

Interactions should feel like manipulating a tool:

- Open a panel.
- Inspect.
- Compare.
- Mark.
- Validate.
- Archive.
- Expand a line.
- Review history.
- Pin an item.
- Filter as if adjusting a lens.

Avoid decorative animation. Use motion to reveal structure, state, and continuity.

## State Design

Design these states explicitly:

- Empty.
- Loading.
- Error.
- Blocked.
- Success.
- Partial data.
- Too much data.
- Review.
- Conflict.

States should preserve the chosen surface identity. Prefer contextual process indicators over generic spinners when possible.
